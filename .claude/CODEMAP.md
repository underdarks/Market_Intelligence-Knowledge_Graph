# MIKG 코드 하네스

## A. 설계 규칙
1. 로드맵에 확정된 변경 지점만 처음부터 클래스·Protocol로 만든다. 추측성 추상화 금지.
2. DB·API·LLM·설정값을 가진 객체는 생성자 주입. 순수 로직은 함수로 직접 호출.
3. 판단(plan)과 실행을 분리한다. 판단은 순수 함수/클래스로 두고 표 기반 테스트.
4. 의존 방향: api → orchestration → generation/search/entity_linking → schema.
   역방향 import 금지. 계약(DTO, 이벤트, enum)은 schema에 한 번만 정의.
5. 새 타입을 만들기 전에 같은 개념의 기존 정의가 있는지 확인한다.
6. 계층이 다른데 같은 단어를 쓰지 않는다 (answer, router). 공개 시그니처에 DB명 등 구현 세부 금지.
7. 설정값은 .env/config, 없으면 기동 시 실패.
8. 함수 vs 클래스 판단 (설계 시 반드시 체크):
   아래 중 하나라도 로드맵·결정사항에 있으면 처음부터 클래스로 만든다.
   - 설정값을 받게 될 예정 (임계값, 상한, top_k 등)
   - 규칙·분기가 늘어날 예정 (유형 추가, 검색기 추가)
   - 구현을 바꿔 끼울 예정 (스텁 → 실제, 사전 → ES)
   - 외부 연결을 가질 예정 (DB, API, LLM)
   해당 없음이 확인된 순수 변환 로직만 함수로 둔다.
   설계안에 "함수/클래스 선택 근거" 한 줄을 반드시 적는다.

## B. 작업 절차 (웹 환경: 사용자가 직접 타이핑)
1. 코드 전에 "의존하는 기존 코드" 목록을 먼저 제시한다.
   내용을 모르면 추정하지 말고 붙여달라고 요청한다.
2. 새 작업: 작업정의서 → 플로우 → 태스크 → 코드.
3. 설계 변경 시 영향받는 파일·테스트 목록을 먼저 보여준다.
4. 코드는 파일 경로 + [신규/교체/추가] 표시 + 바뀐 부분만.
   보일러플레이트·파싱은 완성 코드, 비즈니스 로직은 번호 의사코드.
5. 태스크마다 검증 방법을 준다: 실행 명령 + 기대 결과 (n passed, 로그 문구).
6. 태스크마다 "실무에서는" 한 줄.

## C. 세션 연속성
1. 세션 시작: 인수인계 블록 + CODEMAP 기준으로 시작한다.
2. 태스크 완료: 인수인계 블록(완료/진행/결정/남은/백로그)과 CODEMAP 갱신분을 제시한다.
3. CODEMAP.md (사용자 관리): 디렉터리 트리, 공개 클래스·함수 시그니처, DTO·이벤트 정의.
